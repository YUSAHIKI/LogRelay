## 1. 目的

LogRelayの記録トリガーをWearOSへ拡張する。ウォッチは記録ロジックを持たず、タップ時刻と利用可能な位置情報をフォンへ渡す薄いトリガーとする。DB書き込み、day-boundary判定、「後から追加」注記はフォン側の既存共通処理を使用する。

**v1スコープ**：位置ソースは`watch_gps`（ウォッチGPS成功時）と`manual_pending`（それ以外すべて）の2種類に限定する。`phone_gps_pending`（フォンの位置で補完する経路）は、実機検証で背景状態でのフォンGPS取得が成功保証できないことが判明したため（付録A.5、A.7）、複雑さに見合わないと判断しフェーズ2へ先送りする（付録B）。

## 2. 配布・アプリ識別要件

- 既存LogRelayプロジェクトへ`wear`モジュールを追加する。
- フォン版とWear版は同一applicationId、同一署名、互換性のあるversionCodeでビルドする。
- タップごとのDataItemパスは`/log-trigger/{uuid}`とし、未送信データの上書きを防ぐ。
- GitHub Releases配布中はWear APKをsideloadする。Play Store経由の自動インストールは前提にしない。
- 新規依存関係：`play-services-wearable`（DataClient/NodeClient）を`wear`モジュールおよび`app/build.gradle.kts`に追加する。

## 3. トランスポート

DataClientを使用し、MessageClientは使用しない。

- 接続中: DataItemを同期する。
- 未接続: DataClientのローカル保持と再接続時同期を利用する。
- 独自キューは実装しない。
- `putDataItem()`の成功はローカルData Layerへの登録成功を示し、フォンでの処理完了を意味しない。
- フォンは処理完了後にDataItemを削除する。

**v1での簡略化**：v1はsourceが`watch_gps`／`manual_pending`の2値のみであり、どちらもDataClientの標準同期（接続中は即時、未接続時は再接続時）で完結する。**NodeClientによる接続確認はv1では不要**（後述）。

## 4. Payload（v1）

| キー | 型 | 必須 | 内容 |
|---|---|---|---|
| `tap_time` | Long | 必須 | ウォッチでタップした時刻（epoch millis） |
| `source` | String | 必須 | `watch_gps` / `manual_pending`（v1）。`phone_gps_pending`はフェーズ2で追加予定（付録B） |
| `lat` | Double | 条件付き | `watch_gps`の場合のみ |
| `lng` | Double | 条件付き | `watch_gps`の場合のみ |

## 5. ウォッチ側処理（v1）

### 5.1 起動＝記録方式（案A）

**Wear側アプリは記録トリガー専用とし、起動された時点で記録処理を実行する。**

- 記録開始のためのユーザータップは不要。
- `auto_send`extraによる分岐は廃止する（後方互換のため残す場合も、動作分岐には使わない）。
- 副作用として、ランチャー／アプリ一覧から通常起動した場合も記録される。Wear側アプリは記録以外の機能（履歴閲覧、設定等）を持たないため、「起動＝記録意図」と見なす前提で許容する。
- 誤操作による記録が発生しうるが、LogRelay側で記録の削除が可能なため実害は限定的と判断する。

**この方式を採る理由**：Galaxy Watchのホームキー二回押し割り当ては「アプリ」単位でしか指定できず、ランチャー起動と同一のIntent（extraなし）でメインActivityが起動される。記録専用Activityを別途用意しても割り当て先として選択できないため、メインActivity自体を記録トリガーとする必要がある。

### 5.2 Activityライフサイクル方針（1起動1記録）— 検証済み

初回起動は成功するが、タスクが残った状態での2回目の物理ボタン押下では、Activityの新規起動ではなく既存画面の再表示となり記録が発火しない問題があった（付録C.7）。これを以下の方式で解消した（付録Dで検証済み）。

**記録完了後にActivityを正常終了させる**（OSによる強制的なタスクキルは行わない）。

1. 物理ボタン2回押し（またはTile／ランチャー）で起動
2. 自動記録を実行
3. 「受付済み」を約1.2秒表示
4. `finishAndRemoveTask()`で画面とタスクを終了
5. 次回の起動は必ず新規起動となり、自動記録が発火する

**設計上の要点**：

- **記録の実行は`onCreate()`のみで行う。`onResume()`／`onStart()`では実行しない。** これらのタイミングで記録すると、権限ダイアログからの復帰や画面切り替えでも重複記録が発生しうる。
- **`onCreate()`内でも記録実行を1回限りにガードする。** Activity再生成（プロセス再生成、コンフィグ変更等）で`onCreate()`が再度呼ばれる可能性があるため、`savedInstanceState == null`の場合のみ記録する、または記録実行済みフラグを保持する。
- **「もう一度記録」ボタンは削除する。** このボタンが残っていると、`finishAndRemoveTask()`までの短い表示時間内にタップされ、同一起動で2レコードが生成されうる。**1起動1記録に統一する。**
- **副次的効果**：`finishAndRemoveTask()`によりrecents（アプリ切り替え画面）にも残らないため、「記録トリガーであって滞在するアプリではない」という性質がOSレベルの見た目とも一致する。ウィジェット／NFCタップが画面に何も残さない振る舞いと揃う。

### 5.3 既知の挙動：処理完了前の再起動

GPS取得に最大8秒、その後のフィードバック表示に約1.2秒かかるため、**処理が終了する前に再度起動すると、新規Activityではなく既存Activityへ`onNewIntent`としてIntentが渡される**。v1は`onCreate()`のみで記録するため、この2回目は記録されずに破棄される。

- **挙動の方向性**：二重記録ではなく記録漏れ側に倒れるため、誤ったデータが残るリスクはない。
- **実操作での発生可能性**：「受付済み」画面が表示されている最中に再度二回押しをする動機は通常なく、画面が閉じてから次を押すのが自然な操作となるため、発生頻度は低いと見込まれる。
- **v1での扱い**：判明した挙動として記録するに留め、対応は行わない。将来的に問題化した場合は、`onNewIntent`で「処理中」表示を出す、またはGPSタイムアウト（8秒は保守的な値）を短縮する等の対応が考えられる。

### 5.4 記録処理フロー

起動時（`onCreate()`）に以下を順番に実行する。

1. `tap_time`を即時確定する。
2. ウォッチGPSでFixを試行する。タイムアウトは5〜10秒の範囲とし、実装では8秒とする。
3. Fix成功時は`watch_gps`とlat/lngを送信する。
4. Fix失敗、GPS非搭載、位置権限なしの場合は、フォンとの接続状態を問わず即座に`manual_pending`を送信する。

**v1でNodeClientを使わない理由**：DataClientは接続の有無に関わらずローカル保持→再接続時同期を行うため、送信前に接続状態を確認する意味がない。旧設計でNodeClientを使っていたのは`phone_gps_pending`か`manual_pending`かを判定するためだけであり、その分岐自体がフェーズ2送りになったことで、NodeClient依存・切断直後の誤判定（付録A.5 制約4、A.4.4）はv1では発生し得ない問題として解消される。

### 5.5 トリガー手段一覧

| トリガー | 対応範囲 | 状態 |
|---|---|---|
| Wear Tile タップ | 汎用Wear OS | TileService登録済み・実タップ未検証（UI設計時に確認） |
| ランチャー／アプリ一覧からの起動 | 汎用Wear OS | 案Aにより記録トリガーとして機能 |
| ホームキー二回押し | **Galaxy Watch（One UI Watch）固有** | **実機の物理ボタン操作で動作確認済み**（付録D） |

ホームキー二回押しは、ウォッチ設定 →「高度な機能」→「ホームキー」→「2回押し」からユーザーが手動でアプリを割り当てる。アプリ側で登録するAPIは存在しないため、設定手順のユーザー案内が必要。他社Wear OS端末では同等機能が存在しないか挙動が異なるため、Galaxy Watch限定の付加的トリガーとして位置づける。

## 6. フォン側処理（v1）

WearableListenerServiceの`onDataChanged`で`/log-trigger/`を受信する。

### 6.1 `watch_gps`

- Payloadのlat/lngをそのまま使用する。
- 記録時刻には`tap_time`を使用する。
- `isManualPast`は`false`とする。
- lat/lngが欠落している場合は不正Payloadとして位置なしへ格下げし、診断ログを残す。

### 6.2 `manual_pending`

- 位置情報なしで記録する。
- 記録時刻には`tap_time`を使用する。
- **`isManualPast`は常に`true`とする（条件分岐なし）**。
- **day-boundary判定は記録時には行わない**。`manual_pending`はユーザーによる時刻選択を伴わず、`tap_time`はウォッチで確定した実際のタップ時刻であるため、入力範囲を制限する対象が存在しない。`RelayLabCommon.startOfLogicalDay`は記録後のグルーピング／エクスポート時に既存ロジックとして機能すれば足りる。
  - 補足：既存の手動過去入力機能でday-boundaryが必要だったのは、ユーザーが任意の過去時刻を選ぶ際の**入力制限**としてであり、`manual_pending`にはその要件がない。
- **注記の意味に関する補足（意図的な再利用）**：この注記はもともと「位置情報が記録操作時点のものと必ずしも一致しない」という時間的ズレの警告として設計されたが、`manual_pending`では位置情報自体が存在しないため、警告の性質が実質的に異なる（時間差の警告ではなく、位置なしそのものの明示）。ユーザー向け表示は統一したまま据え置く（表示パターンを増やさない）が、コード上には「意図的な再利用であり実装漏れではない」ことをコメントで明記する。

#### v1.0での判断（追記）

`manual_pending`（位置情報なし）と、既存の手動過去入力機能における「後から追加」（位置情報はあるが記録時刻とのズレがある）は、注記の性質としては本来異なるものである。この区別を表示上も分ける案を検討したが、以下の理由によりv1.0では区別せず、表示は統一のまま進めることとした。

- WearOS Companion機能自体がv1.0のリリース対象外（非公開機能）であり、現時点でこの区別に実装コストをかける優先度は低いと判断した
- 実運用上、「ウォッチ側・フォン側の両方で位置情報を取得できない」というケースは、現在の想定利用シーンでは発生頻度が低いと考えられる（ウォッチのGPS取得失敗が`manual_pending`の主因であり、フォン側のGPS状態とは別問題であるため）

この判断は、WearOS Companion機能の正式リリース時（フェーズ2以降）に再検討する。再検討の際は、表示文言を「位置情報なし」「後から追加（時刻ズレ）」のように分離する案を出発点とする。

### 6.3 共通処理・UUID重複排除

- 新しいDB記録ロジックは作らず、ウィジェット／NFCと共通の既存関数を呼ぶ。
- **重複排除方式**：処理済みIDの別テーブル管理やメモ化は行わず、LogRelayの記録テーブルに`sourceTriggerId`（nullable、UNIQUE制約）カラムを追加する。
  - ウィジェット/NFC経由の記録は常に`null`のまま、既存動作を変えない。
  - WearOS経由の記録のみDataItemのUUID（36文字）を`sourceTriggerId`として書き込む。
  - INSERT時に`SQLiteConstraintException`（制約違反）が発生した場合、それをそのまま「処理済み」と判定する。DB書き込みと重複チェックが同一トランザクションになるため、別レイヤーでの原子性担保が不要になる。
  - Roomスキーマ v5 → v6 のマイグレーションとして実装済み（付録C）。
- 記録成功後（重複判定も含む）にDataItemを削除する。
- 記録失敗時は、再試行方針が確定するまでDataItemを削除しない。

## 7. UI・フィードバック

- Wear Tileは画面オン・アクティブ状態でのみタップ可能とする。
- 起動後は「受付済み」を約1.2秒表示し、`finishAndRemoveTask()`で終了する（第5.2節）。この値は実機検証で連続起動を妨げず、かつ視認可能な長さとして確認済み（付録D）。
- 「送信OK」はDataClientへの登録完了を意味し、フォン記録完了を意味しないことに注意する。
- 「もう一度記録」ボタンは削除する（第5.2節）。
- 振動フィードバックの有無、Tileデザインは別途決定する（第9節）。

## C.6 仕様との差異確認（解決済み）

検証時、`manual_pending`の`isManualPast`が常に`true`になる点が、旧仕様書の「同日内判定とday-boundaryを使用する」という記述と整合しないのではないかとの指摘があった。

## C.7 ホームキー二回押し（Galaxy Watch）— 付録Dで解消

ウォッチ設定からLogRelay Wearアプリをホームキー二回押しに割り当て、動作を確認した。

**初回起動**

- アプリ起動：成功
- 記録到達：未達（当時の実装では起動後に画面上のタップが必要）
- 原因：ホームキー二回押しはランチャー起動と同一のIntent（extraなし）でメインActivityを起動するため、`auto_send`extraによる自動送信分岐に入らない

**タスク残存時の連続起動**

- 2回目の物理ボタン押下：既存画面の再表示となり、記録が発火しない
- 原因：ウォッチアプリのタスクが残っているため、Activityの新規起動が行われない
- 対応：OSによる強制的なタスクキルは不要。記録完了後に`finishAndRemoveTask()`でActivityを正常終了させる（第5.2節）→ 付録Dで実装・検証済み
- 補足：`onResume()`／`onStart()`での記録実行は、権限ダイアログからの復帰や画面切り替えで重複記録を招くため採用しない

# 付録B: フェーズ2参考設計（未実装）— `phone_gps_pending`

v1では実装しないが、設計内容は検証結果とあわせて記録として保持する。フェーズ2着手時に本節を出発点として再検討する。

## B.1 ウォッチ側処理（フェーズ2案）

GPS Fix失敗、GPS非搭載、位置権限なしの場合、NodeClientで接続ノードを確認する。

- 接続ノードがあれば`phone_gps_pending`、なければ`manual_pending`を送信する。
- NodeClientの接続状態は切断直後に古い可能性があるため（付録A.4.4で実測：全無線停止後20秒でも接続済みと誤判定）、ここで決めるsourceは送信時点の推定値に過ぎない。最終的な位置あり／位置なしの判断はフォン側で行う必要がある。

## B.2 フォン側処理（フェーズ2案）

- 受信時にフォン自身の現在地を取得する。取得位置だけを補完し、記録時刻にはウォッチの`tap_time`を使用する。タイムアウト目安は10秒。
- GPS取得失敗、権限不足、バックグラウンド制限、null応答の場合は、位置なしの「後から記録」相当へ格下げする。
- `processed_time - tap_time`が許容時間（初期値候補1〜2分）を超えた場合も、フォン現在地を取得せず位置なしへ格下げする。

## B.3 位置権限（フェーズ2案）

- `ACCESS_FINE_LOCATION`の「アプリ使用時のみ」では、背景のWearableListenerServiceから現在地を安定取得できない（付録A.4.3で実測確認）。
- Xiaomiのバッテリー「制限なし」および未使用アプリ一時停止OFFでも、この位置制限は解消しなかった。
- `ACCESS_BACKGROUND_LOCATION`は要求負担とストアポリシーへの影響があるため、フェーズ2でも採用可否は別途検討する。
- フォンGPSはベストエフォートとし、失敗時は位置なしへ格下げする方針は維持する。

## B.4 フェーズ2着手条件（目安）

- v1運用で「ウォッチGPS失敗により`manual_pending`になる頻度」が実際にユーザー体験上の課題になるかを見てから再検討する。
- Galaxy Watch以外の非GPS搭載ウォッチへの対応ニーズが顕在化した場合も再検討のきっかけとなる。

# 付録A: PoC実機検証報告書

- 作成日: 2026年8月22日
- 対象コミット: `c8073de`（GPSフォールバック実装）、`f266678`（Data Layer用applicationId統一）

## A.4 実測内容

### A.4.1 `watch_gps`

- ウォッチ内蔵GPSが8秒以内にFixした。
- `source=watch_gps` とlat/lngがDataMapに格納された。
- フォンは同一UUIDのDataItemを受信し、座標を変更せず保存した。
- タップからフォン受信まで約4.7秒だった。

### A.4.2 `phone_gps_pending`（付録B関連）

- ウォッチの位置権限を一時的に外し、GPS失敗を確実に発生させた。
- NodeClientが接続中のフォンを検出し、`source=phone_gps_pending`を送信した。
- フォンアプリが前面の場合、約1.6秒でフォン現在地を補完した。
- フォンをホーム画面へ移した直後の一部試験でも取得に成功したが、後続の再現試験では「アプリ使用時のみ」の権限では取得できなかった。OSがアプリを背景状態と判定するタイミングによって結果が変動するため、安定動作とは判定しない。

### A.4.3 フォンのバックグラウンド位置制限（付録B関連）

以下の設定で再検証した。

- 位置権限: 「アプリ使用時のみ」
- Xiaomiバッテリーセーバー: 「制限なし」
- 「未使用の場合はアプリのアクティビティを一時停止する」: OFF
- 省電力除外リストへの登録: 端末上で確認済み

DataItemは約1.6秒で受信・保存されたが、フォンGPSは取得できず、lat/lngはnull、noteは「フォンGPS取得失敗または位置情報権限なし」となった。

この結果から、DataClient受信についてはXiaomi独自のバックグラウンド停止が発生していない。一方、位置取得失敗はXiaomi省電力設定を解除しても変わらず、Android標準のバックグラウンド位置権限制限が主因と判断する。

### A.4.4 切断と遅延同期

フォンのBluetooth、Wi-Fi、モバイルデータを停止して20秒待った後も、ウォッチのNodeClientは一時的にフォンを接続済みとして返した。そのため生成されたsourceは`manual_pending`ではなく`phone_gps_pending`だった（付録B関連）。

通信復帰後、DataItemはタップから約32秒後に自動同期された。**DataClientのローカル保持と再接続時同期はv1にそのまま適用される確認事項**。NodeClientの接続情報は切断直後に古い状態を返す可能性がある、という点は付録Bにのみ関連する。

## A.5 判明した制約

1. フォン版とWear版は同一applicationId・同一署名で配布する必要がある。（v1適用）
2. 「アプリ使用時のみ」の位置権限では、WearableListenerServiceが背景で受信した際のフォンGPS取得を保証できない。（付録B関連）
3. Xiaomiのバッテリー「制限なし」はDataClient受信安定化には有用だが、Androidの位置権限を代替しない。（付録B関連）
4. NodeClientの`connectedNodes`は切断直後に古い接続状態を返す可能性があり、`manual_pending`判定は即時かつ確実ではない。（v1ではNodeClientを使わないため無関係。付録Bでのみ有効な制約）
5. Wear画面がスリープ／非アクティブの場合、タップ操作は受け付けられない。（v1適用）

## A.6 推奨対応（付録B向け）

- `phone_gps_pending`でフォンGPS取得に失敗した場合は、位置なしの「後から記録」相当へ格下げする。
- `tap_time`とフォン処理時刻の差が一定時間を超えた場合も、同じく位置なしへ格下げする。
- `ACCESS_BACKGROUND_LOCATION`は、権限負担と配布ポリシーへの影響が大きいため、フェーズ2でも慎重に検討する。
- Xiaomi端末ではバッテリー設定「制限なし」を推奨設定として案内できるが、必須条件やGPS成功保証として扱わない。

## A.7 結論

DataClientによる送受信、ユニークパス、遅延同期、`watch_gps`、履歴永続化、処理後削除は実用可能と判断する（v1で採用）。

`phone_gps_pending`については、フォンが背景状態のGPS補完とNodeClientによる切断判定が成功を保証できないことが判明した。実利用シーン（フォンがポケット等に格納された背景状態）ではこの経路の実効性が限定的であるため、v1では`watch_gps`＋`manual_pending`のみとし、`phone_gps_pending`はフェーズ2（付録B）へ先送りする。
